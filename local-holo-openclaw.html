Holo 3.1 + OpenClaw: a complete local coding-agent setup

Yali Nie · September 28, 2026

This is my reproducible setup log for turning Holo 3.1 into a local coding assistant on Ubuntu. It starts from the machine and software environment, continues through llama.cpp and model serving, then connects the model to OpenClaw, fixes the workspace configuration, and finally exposes the OpenClaw Web UI securely to my Mac without publishing the service to the Internet.

0. What I wanted to build

The goal was not full desktop automation. I wanted a local workflow similar to a coding agent: the model should be able to read a project, create and edit files, use project tools, verify its work, and eventually run/debug code in an iterative loop.

2. Directory layout

I kept the entire local-model setup under ~/holo31:

~/holo31/
├── llama/
│   ├── llama-b11146/
│   └── cudart-llama-b11146-bin-ubuntu-cuda-12.8-x64/
├── models/
└── test-project/

The important llama.cpp binaries are inside ~/holo31/llama/llama-b11146/. The CUDA runtime distributed for this build is in:

~/holo31/llama/cudart-llama-b11146-bin-ubuntu-cuda-12.8-x64/

3. Make the llama.cpp CUDA runtime visible

Before running the CUDA-enabled llama.cpp binaries, I added their runtime-library directory to LD_LIBRARY_PATH:

export LD_LIBRARY_PATH="$HOME/holo31/llama/cudart-llama-b11146-bin-ubuntu-cuda-12.8-x64:$LD_LIBRARY_PATH"

To avoid retyping it in each new shell, the same export can be placed in ~/.bashrc, followed by:

source ~/.bashrc

I then verified that llama.cpp could actually see the GPU:

~/holo31/llama/llama-b11146/llama-bench --list-devices

The working setup detected CUDA device 0 as the RTX 4080 SUPER with compute capability 8.9.

4. Model and cache

The model used in this setup is:

Hcompany/Holo-3.1-35B-A3B-GGUF:Q4_K_M

I use a dedicated llama.cpp model cache:

export LLAMA_CACHE="$HOME/holo31/models"

The downloaded snapshot was stored under:

/home/yxk/holo31/models/
└── models--Hcompany--Holo-3.1-35B-A3B-GGUF/
    └── snapshots/
        └── 95dd5447a6f101de041c7f03821dafac2bac19a4/

The main GGUF is roughly 21.3 GB and the multimodal projection file is roughly 0.9 GB. Since the main model alone is larger than the 16 GB GPU, this should not be thought of as a full-GPU-resident configuration. The practical setup uses the resources available across the machine.

5. Start Holo with llama.cpp

This is the server command that ultimately worked for OpenClaw:

cd ~/holo31

LLAMA_CACHE="$HOME/holo31/models" \
./llama/llama-b11146/llama-server \
  -hf Hcompany/Holo-3.1-35B-A3B-GGUF:Q4_K_M \
  --host 127.0.0.1 \
  --port 8080 \
  --ctx-size 32768 \
  --parallel 1 \
  --image-min-tokens 1024

The server is intentionally bound to 127.0.0.1. OpenClaw runs on the same Ubuntu machine, so there is no reason to expose the model API directly to the LAN or Internet.

Why 32K context?

I initially tried a 4096-token context. That failed because the OpenClaw agent/system prompt was already around 14,229 tokens before a useful conversation even started. A 4K context therefore could not contain the agent instructions. Restarting llama.cpp with --ctx-size 32768 solved the problem.

If memory pressure becomes too high, 16384 is a possible fallback to test, but 32K is the configuration that worked in this setup.

6. Install and check OpenClaw

OpenClaw was installed globally with npm. After installation, I verified the runtime and OpenClaw version:

node --version
npm --version
openclaw --version

The versions used here were Node.js 24.21.0, npm 11.19.0, and OpenClaw 2026.9.6.

7. Onboard OpenClaw against the local Holo endpoint

With llama.cpp already listening on port 8080, I configured OpenClaw to treat it as an OpenAI-compatible custom provider:

openclaw onboard --non-interactive --mode local \
  --auth-choice custom-api-key \
  --custom-base-url http://127.0.0.1:8080/v1 \
  --custom-model-id "Hcompany/Holo-3.1-35B-A3B-GGUF:Q4_K_M" \
  --custom-provider-id llama-cpp \
  --custom-compatibility openai \
  --custom-text-input \
  --accept-risk \
  --skip-health

OpenClaw stores its configuration in:

~/.openclaw/openclaw.json

Before later editing the workspace configuration, I made a backup:

cp ~/.openclaw/openclaw.json ~/.openclaw/openclaw.json.backup

8. Verify that OpenClaw can talk to Holo

A minimal agent test was:

openclaw agent --local \
  --message "Reply with exactly: Holo local model works."

After increasing llama.cpp to the 32K context window, this succeeded. At this point the chain was working:

OpenClaw → http://127.0.0.1:8080/v1 → llama.cpp → Holo 3.1

9. Start the OpenClaw Gateway and Web UI

The Gateway provides the browser UI:

openclaw gateway run

The local Web UI is served on port 18789. Running:

openclaw dashboard

showed the dashboard address as http://127.0.0.1:18789/. The Gateway expects its authentication token; I keep that token private rather than putting it into notes or chat messages.

10. First coding test — and an important workspace trap

I created a small sandbox project:

mkdir -p ~/holo31/test-project
cd ~/holo31/test-project

cat > README.md <<'EOF'
# Holo Test Project

A sandbox project for testing Holo 3.1 coding capabilities.
EOF

I then asked Holo to inspect the project and create a simple personal homepage. Holo reported that it had created index.html, but the file was not in ~/holo31/test-project.

The reason was important: OpenClaw's agent workspace is configured independently of the terminal's current working directory. The file had actually been created in:

/home/yxk/.openclaw/workspace/index.html

I checked the agent configuration:

openclaw config get agents

Both the default and main-agent workspace were pointing to /home/yxk/.openclaw/workspace.

11. Point the agent at the actual project

I changed both workspace settings explicitly:

openclaw config set agents.entries.main.workspace \
  '"/home/yxk/holo31/test-project"' --strict-json

openclaw config set agents.defaults.workspace \
  '"/home/yxk/holo31/test-project"' --strict-json

Then I verified the result:

openclaw config get agents

Both paths now pointed to /home/yxk/holo31/test-project.

The second coding prompt asked Holo to read README.md, build a small portfolio website with a “Hello from Holo” heading plus About and Projects sections, create any required CSS, verify the generated files, and avoid modifying anything outside the workspace.

This time Holo created index.html and styles.css in the intended project. That was the key proof that OpenClaw + Holo could operate as a project-scoped coding agent rather than just a chatbot.

12. Browser automation experiment

OpenClaw's dedicated headless Chrome was also tested. I deliberately used a strict SSRF/hostname allowlist rather than giving the agent unrestricted browsing. The test allowlist contained only example.com and iana.org.

Holo could inspect Example Domain and identify its “Learn more” link. That was enough to validate browser observation, but it also made the desired boundary clearer: full Computer Use is not necessary for this workflow.

My preferred permission model is narrow: project files, coding tools, and selected browser access when useful. I do not want the local agent to have unrestricted mouse/keyboard control, root access, or broad desktop automation.

13. Access OpenClaw from a Mac without exposing it publicly

The Ubuntu machine's LAN address during setup was 192.168.31.75. From the Mac, I create a local SSH tunnel:

ssh -N -L 18789:127.0.0.1:18789 yxk@192.168.31.75

While that SSH session remains open, I use this address in the Mac browser:

http://localhost:18789/

The traffic path is therefore:

Mac localhost:18789
        │
        │ encrypted SSH tunnel
        ▼
Ubuntu 127.0.0.1:18789
        │
        ▼
OpenClaw Gateway

For access away from the home LAN, the Ubuntu machine also had a Tailscale address 100.112.144.118. With both machines on the same Tailscale network, the equivalent tunnel is:

ssh -N -L 18789:127.0.0.1:18789 yxk@100.112.144.118

This keeps the Gateway bound to localhost instead of opening port 18789 directly to the public Internet.

14. What must be running during normal use

There are two Ubuntu-side processes in the current manual setup:

Terminal / process 1:
llama-server
    └── loads and serves Holo 3.1 on localhost:8080

Terminal / process 2:
openclaw gateway run
    └── serves OpenClaw on localhost:18789

When using the UI from the Mac, the Mac also needs the SSH tunnel process.

15. Why I am not enabling auto-start

I intentionally decided not to launch Holo automatically at boot. The model is large, the GPU has 16 GB of VRAM, and this workstation is also used for CARLA. Keeping a 35B model loaded all the time would reserve resources for a service I do not continuously need.

The preferred workflow is therefore:

Need local coding agent
    → start llama-server
    → start OpenClaw Gateway
    → create SSH tunnel from Mac
    → work in the browser

Need GPU/RAM for CARLA or other work
    → stop Holo/OpenClaw processes

A future quality-of-life improvement is to wrap the long commands in simple manual holo-start and holo-stop scripts. That would reduce typing without turning the model into a boot-time service.

16. Troubleshooting notes

OpenClaw says the context is too small

The initial 4096-token context was insufficient because OpenClaw's prompt itself was about 14K tokens. Restart llama.cpp with a larger context, such as the working --ctx-size 32768 configuration.

Holo says it created a file, but it is not in the current directory

Check the configured workspace rather than assuming OpenClaw inherits the shell's working directory:

openclaw config get agents

llama.cpp cannot find its CUDA runtime libraries

Check that the bundled CUDA runtime directory is present in LD_LIBRARY_PATH:

echo "$LD_LIBRARY_PATH"

The Mac cannot open the OpenClaw page

Confirm that openclaw gateway run is running on Ubuntu and keep the SSH tunnel terminal open on the Mac. The Mac browser should connect to localhost:18789, not directly to Ubuntu's localhost address.

GPU memory pressure

This machine is also used for CARLA, which can consume substantial VRAM. I avoid running CARLA and a large local model unnecessarily at the same time. The model is larger than the GPU's VRAM, so resource usage should be monitored rather than assuming everything is GPU-resident.

18. Next test

The next meaningful benchmark is not another installation test. I want to give Holo a deliberately broken Python or C++ project and test the complete engineering loop:

read project
    ↓
run program / tests
    ↓
observe error
    ↓
locate cause
    ↓
edit code
    ↓
rerun
    ↓
repeat until tests pass

If that loop works reliably, the setup becomes genuinely useful for local software development rather than merely demonstrating that a local LLM can generate files.
