Building a local coding agent with Holo 3.1 and OpenClaw

Yali Nie · September 28, 2026

Tonight I turned a local Holo 3.1 model into a practical coding agent: llama.cpp serves the model, OpenClaw provides the agent and workspace tools, and a browser UI on my Mac reaches the Ubuntu machine through an SSH tunnel.

1. The local model stack

The model is Hcompany/Holo-3.1-35B-A3B-GGUF:Q4_K_M, served locally with llama.cpp. My workstation uses an NVIDIA RTX 4080 SUPER with 16 GB of VRAM. The goal was a useful local agent pipeline rather than full-GPU inference.

LLAMA_CACHE="$HOME/holo31/models" \
./llama/llama-b11146/llama-server \
  -hf Hcompany/Holo-3.1-35B-A3B-GGUF:Q4_K_M \
  --host 127.0.0.1 \
  --port 8080 \
  --ctx-size 32768 \
  --parallel 1 \
  --image-min-tokens 1024

I increased the context to 32K after the initial 4K context was too small for the OpenClaw agent prompt.

2. Connecting Holo to OpenClaw

OpenClaw uses the local llama.cpp OpenAI-compatible endpoint as its primary model. This turns the model from a plain chat endpoint into an agent that can work with project files and tools inside a defined workspace.

I deliberately did not give the model full Ubuntu desktop control. For coding, project-level file and command access is much closer to what I actually need.

3. Browser-agent validation

I tested OpenClaw's dedicated headless Chrome with a strict hostname allowlist. Holo successfully inspected the Example Domain page, found its “Learn more” link, and reported the destination without clicking it. That verified that the agent could observe browser state through OpenClaw.

The test also clarified the actual goal: not a model that controls the whole computer, but a local coding assistant that can understand a repository, edit files, run code, inspect errors, and iterate.

4. The workspace lesson

OpenClaw does not automatically use the shell's current directory as the agent workspace. My first coding test was launched from ~/holo31/test-project, but Holo created index.html under ~/.openclaw/workspace.

I explicitly changed both the main agent and default workspace:

openclaw config set agents.entries.main.workspace \
  '"/home/yxk/holo31/test-project"' --strict-json

openclaw config set agents.defaults.workspace \
  '"/home/yxk/holo31/test-project"' --strict-json

After that, Holo created a small portfolio website in the intended project, including index.html and styles.css, and verified the requested content.

5. Web UI from a Mac

The OpenClaw Gateway stays on localhost on the Ubuntu machine. Instead of exposing port 18789 publicly, I reach it from the Mac through an SSH tunnel:

ssh -N -L 18789:127.0.0.1:18789 yxk@192.168.31.75

The UI then appears on the Mac at http://localhost:18789/. Gateway authentication remains enabled. For access away from the local network, the same tunnel can use the Ubuntu machine's Tailscale address.

6. Keep the model manual

I do not want Holo to start automatically with Ubuntu. A 35B model consumes substantial memory and GPU resources, while the same workstation is also used for CARLA. The better workflow is to start the AI stack only when needed and stop it when those resources are needed elsewhere.

The next useful test is a real coding loop: give the agent a small Python or C++ project with a bug and see whether it can run it, diagnose the failure, edit the code, and rerun it until the test passes.
