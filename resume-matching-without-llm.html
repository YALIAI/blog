Evidence: matching resumes to jobs without a large language model

Yali Nie · September 30, 2026

I built a lightweight first version of Evidence that retrieves resume evidence for job requirements entirely in the browser. It uses a skill dictionary, explicit rules and TF-IDF rather than a generative model. This creates a baseline to evaluate before adding semantic models or an LLM.

Open the application · Source repository · Implementation snapshot

What this version does

Paste an English job description and up to six resume texts, then select Analyze resume evidence. The report lists extracted criteria, their required/preferred priority, the original job context, exact resume passages and a follow-up question. Reports can be exported as Markdown. A separate manual workspace supports editable criteria, candidate comparison, reviewer notes and CSV export.

This is resume-to-job matching and evidence-report generation. It does not generate or rewrite a resume, verify a candidate's competence, rank candidates or predict hiring probability.

Processing pipeline

  1. Split text: preserve resume passages while splitting at newlines and sentence boundaries.
  2. Extract criteria: detect named skills using a curated alias dictionary. Required and preferred headings set priority. Lines without recognized skills may be retained as generic criteria.
  3. Find direct mentions: use token boundaries to avoid matching Java inside JavaScript or C++ inside C#. Recognize aliases such as Ubuntu for Linux.
  4. Check context: heuristic checks for terms such as “no”, “not”, “learning” and “course” prevent these passages from being treated as direct evidence.
  5. Retrieve lexical hints: if no direct mention is found, TF-IDF cosine similarity retrieves a related passage from that candidate's resume.
  6. Explain the result: display a fixed status, reason and template-based interview question. No generated claims are needed.

TF-IDF implementation

The current implementation is plain JavaScript in src/matcher.mjs. It removes a small English stop-word list, counts terms and computes document frequency across the supplied resume passages. Each term receives weight (1 + ln(tf)) × (ln((N + 1)/(df + 1)) + 1). Cosine similarity compares the job context with each passage. Candidate-specific filtering prevents evidence from being borrowed from another resume.

The retrieval threshold is currently 0.18. It is an uncalibrated heuristic for showing related text, not a confidence level or a probability. A TF-IDF hit is always a verification hint; it never establishes qualification by itself.

Meaning of the report labels

  • Direct skill mention: a named skill appears in an exact resume passage without a detected caution term. Depth, duration and the full job condition are still unverified.
  • Needs verification: a skill appears in limited, learning or negative context, or a passage has related wording.
  • No evidence found: neither a direct mention nor a sufficiently related passage was retrieved. Missing text does not establish lack of ability.

For example, “Researched LiDAR denoising” does not establish multi-sensor fusion experience. “Learning Python in a course” is not treated as direct skill evidence. “Developed C++ modules on Ubuntu” can provide direct mentions for C++ and Linux.

Why this baseline is useful

The analysis needs no model download, API key, GPU or inference server. It runs in the browser and sends no resume or job text to a backend. The site still needs to load its static assets initially. Inputs and manual reviews remain in memory and clear on reload; export any work that should be retained.

The implementation is inspectable: matching reasons and quotes can be traced to dictionary entries, rules and text retrieval. This makes it easier to identify whether an error comes from extraction, missing aliases, context checks or retrieval.

Files and reproducible commands

  • src/matcher.mjs: dictionary, requirement extraction, TF-IDF and report construction.
  • src/App.tsx: input forms, local analysis action, evidence display and Markdown export.
  • src/ReviewBoard.tsx: separate manual review and CSV workflow.
  • tests/matcher.test.mjs: regression checks.
  • docs/app.js: prebuilt browser bundle; docs/styles.css: shared application styles.
git clone https://github.com/YALIAI/evidence-recruitment.git
cd evidence-recruitment
npm install
node --test tests/matcher.test.mjs
npm run build
python3 -m http.server 8000 --directory docs

Use Node.js 22 or later and open http://localhost:8000/. GitHub Pages publishes the prebuilt docs/ folder using the repository's workflow. Source changes must be accompanied by a rebuilt bundle.

Validation performed

Seven regression tests passed: aliases and exact quotations; LiDAR versus fusion; negative and learning context; skill boundaries; preferred headings and preserved context; lexical hints staying unverified; and consistent criteria with candidate-specific evidence. DOM interaction checks passed for text input, local analysis, report rendering and clearing stale reports after editing. Analysis did not call fetch. The production build and GitHub Pages deployment succeeded.

These checks verify implementation behavior, not matching accuracy across real recruitment data. A full browser visual check was not completed because the test browser download failed.

Known limitations

  • English pasted text only; no PDF/DOCX extraction or OCR in this version.
  • The dictionary is mainly technical, automotive and software-oriented.
  • Negation and experience context are heuristic and can misclassify complex sentences.
  • Several skills in one sentence are extracted separately. “Camera or LiDAR” does not become a fully modeled alternative condition.
  • Years, overlapping work dates, proficiency, recency and implicit skills are not inferred.
  • TF-IDF cannot reliably recognize paraphrases or distinguish related experience from sufficient experience.
  • No automatic candidate rejection, ranking or calibrated match percentage is implemented.

Next experiment: evaluate before adding models

Create a manually reviewed set of job requirements and resume passages. Measure missed evidence, unsupported positive matches and the usefulness of retrieved passages. Preserve a separate test set. A small embedding model could then improve paraphrase retrieval; a cross-encoder could refine passage ordering. An LLM could later help interpret compound requirements and draft explanations, while exact quote validation remains in place.

Embeddings, rerankers, an LLM backend and fine-tuning are future experiments, not capabilities of this release. The local rules-and-TF-IDF version stays useful as a reproducible comparison baseline.
